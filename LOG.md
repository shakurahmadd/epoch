## Entry 001 — 2026-04-20
**Phase 0: Project Setup & Folder Structure**

---

### Decisions

**Separate `ml/` from `backend/` as a top-level directory**
- Reasoning: ML training dependencies (PyTorch, xarray, PyTorch Forecasting) are not needed at API runtime. Keeps the API Docker image lean and ownership clear.
- Alternatives rejected: `ml/` nested inside `backend/` — couples training and runtime dependencies, creates merge conflict risk.

**Create a top-level `ingestion/` directory separate from `ml/`**
- Reasoning: Data ingestion (download → clean → load to PostgreSQL) is ETL, not ML training. Runs independently on a schedule or once.
- Alternatives rejected: `ml/data/` — conflates pipeline work with model training work.

**Store model weights on HuggingFace Hub, not in the repo**
- Reasoning: Binary files are too large for Git. Loading from Hub at runtime keeps images lean and decouples model versioning from code deployment.
- Alternatives rejected: Baking weights into Docker image — enormous images, full rebuild on every retrain.

**Commit `.env.example`, never `.env`**
- Reasoning: `.env` contains live secrets. `.env.example` documents required variables without exposing values.
- Alternatives rejected: Committing `.env` — security risk.

### Concepts Learned

**Scaffolding upfront on complex projects**
For multi-service projects, designing folder structure before writing code forces architectural thinking early. Prevents sprawl and makes Docker, .gitignore, and ownership easier to reason about from day one.

**ETL / ingestion vs. ML training**
Ingestion scripts download raw data, clean it, and load it into PostgreSQL. They are a distinct concern from ML training scripts which consume that data. One populates the database, the other reads from it.

**Git is for code, not data or model weights**
Large binary files should never be committed. Model weights live on HuggingFace Hub. Data is downloaded locally or stored in object storage.

**Commit message conventions**
- Imperative mood: "add" not "added"
- Type prefix: `chore` (housekeeping), `feat` (new feature), `fix` (bug fix), `docs` (documentation)
- Message should reflect everything in the change

**Python files to always gitignore**
- `__pycache__/`, `*.pyc` — bytecode auto-generated by Python
- `.venv/` — local virtual environment
- `*.egg-info/` — packaging metadata

### Interview Q&A

**Q: Why did you separate `ml/` from `backend/` in your project structure?**
A: ML training pulls in heavy dependencies that the FastAPI runtime doesn't need. Keeping them separate produces a lean API Docker image and clear ownership boundaries. If a data scientist and backend engineer are working in parallel, they're not stepping on each other.

**Q: Where do your ML model weights live and why?**
A: HuggingFace Hub. They're too large for Git, and storing them externally means the Docker image stays lean. The API loads weights at runtime, so deployment doesn't require rebuilding the image every time a model is retrained.

**Q: What's the difference between `ingestion/` and `ml/` in your repo?**
A: `ingestion/` is ETL — it downloads raw MIDAS and ERA5 data, cleans it, and loads it into PostgreSQL. `ml/` contains training scripts that read from PostgreSQL to train models. Separate concerns: one populates the database, the other consumes it.

**Q: Why commit `.env.example` but not `.env`?**
A: `.env` contains real secrets and must never be committed. `.env.example` shows exactly which environment variables are required without exposing values. It's documentation that lives in the repo.
